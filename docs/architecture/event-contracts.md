# Additive CulinaryOS event contracts

Contract home: `packages/shared/src/types/event-contracts.ts`, exported through the existing shared types barrel. This reuses the payload interfaces in `events.ts`; it does not replace the existing DomainEvent, change event names or alter live broker/routes.

`CulinaryEventV1` discriminates payload by wire name and fixes version to literal1. Supported: order created/cancelled, ticket fired/bumped, course fired, pantry low-stock, menu item sold, table merged/transferred/assistance and reservation seated. Seven reuse existing payload interfaces; four additional interfaces preserve fields from unchanged route producers. These four wires remain outside the legacy EventType union; the additive contract does not silently change old consumers. The other10 catalog events are not accepted: nine have declarations without an evidenced payload producer in the bounded literal-reference scan, and ticket-held is a separate pending_push outbox transport.

`validateCulinaryEventV1(value, expectedTenantId)` checks structural payload fields, finite numeric values, own mandatory properties, exact version/wire and tenant equality. Caller context must come from trusted authenticated authority; deriving expectedTenantId from the event defeats tenant matching. This is neither authentication nor permission granting. Identifiers/timestamps remain strings consistent with existing interfaces; this is not UUID/time semantic certification. Pricing, positive quantities, clinical decisions and business invariants remain authoritative domain responsibilities.

Optional legacy fields, custom station strings and forward-compatible extra properties remain supported. Existing optional payload interfaces reject explicit undefined under exactOptionalPropertyTypes. Transfer orderId/managerId and assistance note explicitly allow undefined because actual producers emit those properties before JSON serialization. Reservation table_id must be present and string or null; nested tenant_id must match the envelope and trusted context. Inherited known optional fields are rejected. Values are not coerced or stripped. The function returns the original object on success; callers must prevent mutation between validation and use. Intended inputs are decoded event data, not executable objects/proxies/accessors; this validator is not an execution sandbox.

Runtime contract tests: `node --test tests/architecture/event-contracts.test.mjs` on the existing Node24 runtime. Compile type assertions with the existing TypeScript compiler under strict, exactOptionalPropertyTypes and noUncheckedIndexedAccess. Tests verify version/discriminator narrowing, eleven payloads, tenant/version rejection, nested malformed values and legacy compatibility. Isolated compiler emit/import checks do not prove broker integration.

Route source parity: set FOUNDATION_TYPESCRIPT to an existing parser and run `node --test tests/architecture/route-event-parity.test.mjs`. It parses seven producer payload sites from tables.ts/reservations.ts, substitutes only allowlisted data expressions across three fixture contexts, and checks both in-memory and JSON shapes. It also reads source-declared version/tenant/source fields; IDs and timestamps are fixtures. Calls and unsupported expressions fail the interpreter. No route, manager-auth, serializer implementation, DB client or provider request is executed; this is source-level simulated parity, not live integration acceptance.

Before any live consumer adoption: inventory actual producer/consumer payloads, run parity fixtures, define per-event version/deprecation behavior and duplicate/replay semantics, test authorization at the domain/API boundary, and preserve rollback to old consumers. Broker/provider transitions and financial/clinical events require their own evidence and approved scope. No live event mutation is authorized by these contracts.
